# SFDX scaffold — project layout, manifests, stub conventions

## Project layout
```
<partner>-poc/
  force-app/main/default/{objects,classes,lwc,flows,...}
  manifest/package.xml
  sfdx-project.json
  .forceignore   (excludes requirements.json and docs/)
```

## Manifests
- `sfdx-project.json` — `sourceApiVersion` 66.0; one packageDirectory (`force-app`); namespace empty for PoC unless 2GP (then set the namespace — flag a placeholder namespace for the user to register on the Dev Hub).
- `package.xml` — one `<types>` block per metadata type present, members enumerated from the component inventory; `<version>66.0</version>`.
- **NEVER list `AiAuthoringBundle` in `package.xml`** (validator check 5.4). Agent Script `.agent` bundles are **not packageable in 2GP** — including the `<types>` block makes package version creation fail. The `.agent` lives in `force-app/` for authoring/preview, but ships to subscribers via an LWC string constant or install doc, NOT in the managed package manifest. (Same reason the `.agent` under a packageDirectory is a known WARN — validator 3.6.)

## Stub conventions (honest scaffold — NO business logic)
- Apex: signatures only, body is a TODO. **Access modifier depends on the packaging decision:**
  - **2GP / managed package** — invocable Apex backing an Agentforce action MUST be packaging-ready even as a stub (validator checks 1.1–1.5), because subscribers invoke it across a namespace boundary:
    - `global with sharing class X` (not `public`)
    - `@JsonAccess(serializable='always' deserializable='always')` on the outer class AND every inner `Request`/`Response` class that holds `@InvocableVariable` fields
    - `global static` on the `@InvocableMethod`
    - `global` on every `@InvocableVariable` field and on the inner classes
  - **Unmanaged / scratch-only PoC** — `public with sharing` is fine.
  - When `decisions.packaging == "2GP"`, generate the `global` form by default for any invocable Apex that backs an agent action. Example stub:
    ```apex
    @JsonAccess(serializable='always' deserializable='always')
    global with sharing class SlackNotifier {
        @JsonAccess(serializable='always' deserializable='always')
        global class Request {
            @InvocableVariable(required=true) global String summary;
            @InvocableVariable global String channel;
        }
        @JsonAccess(serializable='always' deserializable='always')
        global class Response { @InvocableVariable global Boolean posted; }
        @InvocableMethod(label='...') global static List<Response> send(List<Request> r) {
            // TODO (build): ...
        }
    }
    ```
- LWC: component skeleton with `@api` props + TODO; template with structural comment only.
- Objects/fields: full `*-meta.xml` (these are real, deployable config, not stubs).
- Every stub header cites the source feature/use case for traceability.
- **Traceability comments go INSIDE the root element, never before it (nCino run).** A `<!-- Serves: … -->` (or any comment) placed **between the `<?xml …?>` declaration and the root element** breaks `sf project convert source` / `deploy` with `ConversionError: Invalid XML tags or unable to find matching parent xml file for CustomField "<field>"` — the converter can't associate a file whose first node is a comment with its parent object, and the whole deploy dies before reaching the org. Emit the comment as the first line **inside** the root element instead:
  ```xml
  <?xml version="1.0" encoding="UTF-8"?>
  <CustomField xmlns="http://soap.sforce.com/2006/04/metadata">
      <!-- Serves: UC1 … -->
      <fullName>Assigned_RM__c</fullName>
      …
  </CustomField>
  ```
  Applies to every `*-meta.xml` (objects AND fields). Affected all 9 object/field files in the nCino package; deploy only succeeded after relocating the comments.
- **Create a source directory only when writing a file into it** — never leave empty dirs (they don't deploy and git won't track them).

## External / managed-package object references — REQUIRED prompt (never silent-default)
When a field references an object from a managed package (e.g. a partner's managed loan/transaction object) or any object not generated by this package, you MUST ask in Phase A how to resolve it — do NOT silently default to a `Text` field:
- **(a) Declare a package dependency** — the managed package must be pre-installed in the target; the lookup points at the real object. List it in pre-instance config.
- **(b) Local placeholder object** — generate a local `Loan__c`-style object so the PoC stands alone in a clean demo instance.
Record the choice in `requirements.json`. A `Text` placeholder is only acceptable if the user explicitly chooses it, and must carry a TODO noting the real target.

## Permission set (REQUIRED for any generated objects)
Generate a least-privilege permission set granting CRUD/FLS on every generated object/field and access to every generated Apex class, so the deployed package is usable without manual admin work. Add it to `package.xml` (`PermissionSet`). Without it, deployed objects are invisible to users.

## Deploy dry-run validation (optional, when an org is authenticated)
After scaffolding, if an org alias is available:
`sf project deploy start --manifest manifest/package.xml --dry-run --target-org <org>` and report the result. If no org is authenticated, state that validation was skipped — do not claim the package deploys.
